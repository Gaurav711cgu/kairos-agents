## Data gate and exact split rules

1. Freeze a candidate inventory before training. Record the dataset identifier and immutable revision, repository and full source commit, issue identifier, original issue-text digest, source hashes, acquisition date, qualification outcomes and all known exposure events. Keep excluded candidates with reasons. Cross-dataset copies of the same issue are one issue.
2. Build issue-family connected components before splitting. Join aliases, `-scope` variants, the same upstream issue at different commits, backports/cherry-picks, duplicate reports and documented related fixes. Do not strip arbitrary suffixes automatically. Store an explicit alias map. An unresolved family relationship goes to quarantine.
3. Detect exact duplicates using SHA-256 of exact UTF-8 issue, original source and rendered patch bytes. Also compare issue text normalized only by Unicode NFC, CRLF-to-LF and whitespace collapsing. Near-duplicate review uses word-token 5-gram Jaccard similarity of at least 0.80 for issue text or target patches; short texts with fewer than five tokens receive manual review. These are review triggers, not proof of independence. Review adjacent upstream commits and related issues. Join confirmed duplicates to the same component; quarantine unresolved pairs. Boilerplate code appearing in different issues must not by itself establish a positive label.
4. Reject any component touching the existing locked evaluation cohort. Audit against every recorded exposure identifier and original issue digest, including qualification failures, source inspection, local/public captures, prompt examples, hard-negative mining and prior training. Check metadata before opening target patches. Append new exposures to the ledger; never delete old entries. Historical exposed components may be labeled `train` or `diagnostic`, but never `fresh_holdout`. No held-out component may supply training, development, negatives, prompt examples or hyperparameter choices.
5. Reserve previously frozen Phase 3 development/holdout cohorts exactly as frozen. Do not rerun this split algorithm to replace them. For this initial training pilot, form a new eligible pool that excludes those cohorts and every historically exposed component. Existing exposed history stays diagnostic. Reusing it for training would require a separately frozen protocol and cannot create fresh evaluation cases. A curator commits the candidate inventory and split manifest before any model fitting. The training author receives only train/development material.
6. For that new pool, define each component key as the lexicographically smallest canonical `repository#upstream_issue_id` in it. Compute `int(SHA256(UTF8("kairos-cloud013-v1\n" + component_key)).hexdigest(), 16) % 100`. Assign buckets 0–69 to train, 70–84 to development and 85–99 to holdout. All revisions, queries, patches and negatives from a component inherit its assignment. Exact duplicate issue/target content cannot cross splits. Publish component membership and split hashes locally. Do not change the seed or keep adding candidates because holdout outcomes disappoint.
7. The proposed future pilot uses at least 40 distinct training components, eight development components and 16 fresh held-out components, covering at least two repositories, with at least four development and eight held-out components per repository. These configurable study floors must be chosen and frozen before fitting. They are not a theorem about statistical power, a guarantee of broad superiority, or requirements for Phase 2 software or SDE work. If this allocation or qualification cannot supply them, record the shortfall and do not train under this particular protocol. A different protocol needs a new frozen version before fitting. Two successful issues do not pass this proposed training gate.
8. Repair positives require a reproduced failing baseline and passing candidate on the pinned independent verifier, with source/patch/verifier/receipt hashes and exact test counts. Each issue has equal total training weight; multiple valid patches share that issue's weight. Retain failed/unknown trajectories separately with outcome labels. Never promote a failure using an unrecorded or post-hoc check. For retrieval training, use independently reviewed issue-to-original-chunk relevance; an unsuccessful repair is not proof that the retrieved chunk was irrelevant. Mark patch-derived relevance as a proxy and document its incomplete coverage.

Use one reviewed canonical copy of each exact duplicate target per issue/revision. Preserve provenance for removed copies. Different successful patches on one issue do not increase its independent sample count. Negative mining runs within its own split against original source; held-out queries or labels never enter the training miner. Report counts by issue family, repository, outcome and split, before and after deduplication.

## Rights, provenance and export boundary

Review rights separately for issue text, repository source, labels, generated or maintainer patches, dataset packaging and base-model weights. A dataset's license is not automatically a license for every underlying repository or issue. Require the origin URL, exact revision, license identifier or explicit terms reference, a hash of the evidence, required notices and a dated reviewer decision for the intended training and redistribution use. Unknown or conflicting rights mean quarantine; this design does not certify a license. Verify derivative adapter and publication restrictions before model selection or export.

Build a new explicit file allowlist. Never upload a checkout, home directory, `.git`, environment file, key, session/CLI transcript, cookie, private account identifier, private repository material, hidden verification, held-out reference repair, patched source snapshot or raw runtime directory. Other reference repairs are also excluded, except for explicitly rights-reviewed train/development loss targets in a separately versioned repair bundle as described below. Public upstream data still requires rights and privacy review. The current Kairos repository is private; that does not authorize exporting its source, captured logs or credentials. Prepare sanitized public upstream examples independently.

Only train/development inputs and their reviewed supervised labels may enter the training bundle. Keep held-out queries, targets, relevance labels, verifier code and private grading receipts in a separate sealed evaluation store. Repair target patches are permitted only as approved train/development loss targets; never concatenate them into input context. The loader must pass only the documented input fields to the model. All candidate chunks come from pinned original source. Reference paths or line ranges must not seed retrieval selection.

Inspect the final extracted archive, not only its source directory. Reject absolute paths, traversal, symlinks, links outside the allowlist, unexpected files and oversized members. Run a secret/private-data scan and manual review, retain license notices, then hash every exported file and the final archive. A passing scan does not replace rights or human review. Do not publish a dataset, notebook outputs or checkpoints by default. Upload/account actions and actual training remain outside this deliverable.

## Training bundle contract

Use UTF-8 JSON Lines for `train.jsonl` and `development.jsonl`. Each row is one query/candidate pair for the initial retrieval study. Do not place holdout rows in this bundle. All hashes below are lowercase SHA-256 hex; commits/revisions must be immutable identifiers verified at acquisition. A later validator must reject missing/unknown fields and invalid types.

| Field | Type and rule |
| --- | --- |
| `schema_version` | String, exactly `kairos-retrieval-training-v1`. |
| `example_id` | Unique string, SHA-256 of UTF-8 `json.dumps(row_without_example_id, sort_keys=True, ensure_ascii=False, separators=(",", ":"), allow_nan=False)` with no trailing newline. |
| `split` | String, `train` or `development`, matching the frozen manifest. |
| `component_key`, `instance_id`, `repository`, `upstream_issue_id` | Nonempty canonical identifiers; explicit aliases live in the split manifest. |
| `dataset_id`, `dataset_revision`, `source_commit` | Nonempty pinned provenance. No mutable `main` or `latest`. |
| `issue_sha256`, `source_file_sha256`, `chunk_sha256` | Hashes of exact original bytes; normalization hashes are additional dedup metadata. |
| `query` | Reviewed public issue statement only; no reference fix, hidden test, answer hint or evaluation feedback. |
| `path`, `start_line`, `end_line`, `code` | Relative POSIX path; positive inclusive line range; exact original code matching source/chunk hashes. Reject traversal, hidden/denied paths and symlinks. |
| `relevance` | Integer 0 or 1, reviewed label; never an unexamined repair-outcome conversion. |
| `label_provenance` | Object containing annotation method, reviewer, review timestamp and local receipt hash. `patch_proxy` must be named if used. No hidden target contents. |
| `negative_method` | `null` for a positive; otherwise a documented within-split method and miner revision. |
| `rights_refs`, `exposure_refs` | Nonempty lists of keys into the reviewed rights and append-only exposure manifests. |

`manifest.json` records schema version, study purpose, inventory/split/exposure/rights hashes, per-file hashes and byte sizes, source exclusions, per-split component/repository counts, reviewed export decision, reviewer/date and data-gate result. `rights.json` contains component-level evidence and required notices. The allowlisted archive includes those files and notices. Data-gate approval is never inferred from file count or a Boolean supplied by an untrusted upload.

The integrated repair preparation module defines a separate schema with the same identity/rights/split fields plus `original_context`, `target_patch`, `target_patch_sha256`, `baseline_failure_receipt_sha256`, `verification_pass_receipt_sha256` and `verifier_revision`. `outcome` must be `verified_repair`; historical and post-hoc outcome provenance must remain separate. Failed trajectories belong in a separate diagnostic/negative schema. No acquired training rows are provided; see `TRAINING_PREPARATION_013.md` for the implemented schema.

## Cloud preflight and interruption protocol

The included `notebooks/training-preflight013.ipynb` runs standard-library checks only. It does not install packages, download weights, attach a drive, upload data, start training or claim data readiness. Its training cell is disabled and raises if enabled. The cloud account's current free-tier eligibility, allocation, quota and persistence behavior must be inspected in the provider UI at run time. Do not enable paid compute, purchase credits, change billing, use extra accounts or bypass quotas.

1. Record provider, UTC time, Python/OS, actual GPU name/count, driver, total/free VRAM, available system RAM and disk. Check free-tier eligibility and any quota/expiry values exposed by the provider UI. Record unavailable limits as unknown; Colab does not publish fixed free-tier limits. Unknown remaining quota permits only a bounded interruption-safe pilot, not an assumed long allocation. A GPU's product name alone is insufficient. Keep free-tier and quota receipts without exposing account details.
2. Select the smallest justified training profile after allocation. Pin base model/tokenizer identifier and full revision, file hashes, architecture, model license, custom-code review, exact dependency lock, CUDA/backend identity, seed, token limit, microbatch, accumulation, precision, optimizer, learning rate, steps, adapter target modules/rank and trainable parameter count. No compatibility claim is made by this design. Reject unreviewed remote code. No model download is authorized now.
3. Count dependencies, weights, indexes, data and receipts in the existing project-wide 6 GiB local ceiling. Preserve at least 4 GiB free local disk. Export only a bounded approved artifact if local limits cannot hold a checkpoint. Set a separate measured cloud disk budget covering peak cached weights, temporary files and two full resume checkpoints. Cloud capacity does not permit unaccounted local downloads.
4. On actual allocated hardware, run one bounded forward/backward/optimizer step using the longest permitted input and worst permitted batch. Record peak allocated/reserved VRAM, system RAM, step duration, cache growth and free disk. Require at least 15% measured VRAM headroom and 20% measured RAM headroom, plus disk for two complete checkpoints. These are conservative project gates, not universal fit guarantees. A quantized weight-size estimate does not replace this test.
5. Save and reload a complete resume checkpoint, then execute the next bounded step. Require model/base identity, adapter or trained head, optimizer, scheduler, global step, data/sampler position, all RNG states, tokenizer, lock/config and data/split hashes. Verify hashes and resume identity before loading any tensor. Adapter-only export is for inference, not proof of resumable training. Use trusted locally produced checkpoints only.
6. Freeze maximum steps and wall time before the pilot. When remaining quota is unknown, cap the initial fit/resume pilot at ten minutes and the first training segment at thirty minutes; continue only through another explicitly recorded segment under the same frozen configuration. These are project limits, not provider guarantees. Save a complete checkpoint every 50 optimizer steps or five minutes, whichever comes first, and before a planned stop. Two checkpoints must fit without deleting the last valid one. Verify the new checkpoint before retiring the older one. Checkpoint persistence outside the ephemeral VM needs a reviewed manual export or provider save operation; this scaffold does not perform one. Without a verified persistence/recovery path, do not begin a long run.
7. If runtime disappears, resume only from the last verified complete checkpoint. Lost work is recorded. Kaggle-to-Colab fallback uses identical data/split/base/config hashes. Different hardware/backend/library versions get a new run ID and an explicit compatibility/reproducibility note. A successful load does not imply bitwise identical continuation. If resume validation fails, stop; a new run starts from the same frozen protocol and is reported separately.

QLoRA is not an unconditional memory guarantee. Hugging Face documents preparing a quantized model for adapter training with `prepare_model_for_kbit_training`; the actual backend/model/device combination still needs the measured fit and resume tests. The initial retrieval pilot can use a suitable small trainable head or encoder adapter; causal-language-model PEFT snippets must not be copied into an encoder without checking architecture and task support. [Official PEFT quantization guide](https://huggingface.co/docs/peft/developer_guides/quantization).

## Frozen evaluation and release gates

Compare BM25, the frozen existing encoder and the trained retrieval profile on the same pinned source inventory, held-out issue components and returned-context budget. Freeze chunking, token limits, negative-mining settings, training schedule, checkpoint-selection metric and evaluation script before the first held-out run. Select checkpoints on development MRR only, with a deterministic earliest-step tie break. Do not choose a checkpoint by held-out score.

Report file Recall@1/5/10, MRR, changed-region overlap and complete region coverage, with per-issue results, exclusions, latency, indexing time, storage and peak memory. Label patch-derived relevance as a proxy. Cluster uncertainty by issue family; do not count chunks or three patches from two issues as independent repairs. Training loss and retrieval scores do not establish repair improvements.

Only a later frozen repair study can test verified repairs per attempted case under matched provider and call/check budgets. Preserve failures, infrastructure errors, timeouts and unknown dispatches. No held-out retuning, case substitution or cherry-picked seed reruns. Public benchmark pretraining contamination remains unknown. A subset is not a full 300-case SWE-bench Lite score.

Promotion requires all data/rights/exposure gates, measured fit and resume receipts, complete training receipts, deterministic evaluation artifacts and acceptable engineering checks. Failure to improve is a valid result. Keep the frozen baseline if the trained profile regresses or uncertainty prevents a useful conclusion. No score gain, interview result or production reliability is guaranteed.
